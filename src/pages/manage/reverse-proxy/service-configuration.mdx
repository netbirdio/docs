# Backend Service Configuration

For HTTP services, the NetBird reverse proxy sets `X-Forwarded-For` and `X-Real-IP` to carry the client IP to your backend. Many applications require a "trusted proxies" or "known proxies" setting before they use these headers. Configure this setting to match the source of the connection **as seen by the backend**, which depends on how traffic reaches it.

This page covers HTTP backends. For TCP and TLS services, see [PROXY Protocol](/manage/reverse-proxy#step-4-configure-advanced-settings).

<Warning>
    **Cloud-hosted usage limits:** NetBird's cloud-hosted Reverse Proxy is provided on a shared, best-effort basis. High-volume or sustained data transfers may be subject to bandwidth limits, rate limiting, and fair-use policies under the [NetBird Terms of Service](https://netbird.io/terms). These restrictions do not apply if you [self-host NetBird](/selfhosted/selfhosted-guide).
</Warning>

## Identify the source IP

Check the backend's connection logs or untrusted-proxy error messages for the remote address before forwarded headers are applied. Do not use the client address from `X-Forwarded-For` as the trusted proxy entry.

| Backend connection | Source IP the backend sees |
|--------------------|----------------------------|
| Directly to a peer's WireGuard interface | The proxy's NetBird IP. |
| Through a routing peer with [masquerade](/manage/networks/masquerade) enabled | The routing peer's address on the backend's network. Routing without masquerade can preserve the proxy's NetBird IP. |
| Through userspace forwarding, including some container deployments | The address used by the forwarding peer to open the backend connection, which can be a LAN, Docker bridge, or loopback address. |
| With **Direct Upstream** enabled | An address of the proxy host or container, using its local network stack. |

### Docker Bridge Networks

When a NetBird container forwards requests to a backend on the same Docker bridge, the backend may see the NetBird container's bridge IP. The request can still arrive at the NetBird container through a WireGuard tunnel; the final hop to the backend uses the bridge network.

Use `docker network inspect <network>` to check the container addresses and subnet, then match them against the backend's observed connection source. Trust the forwarding container's address when it is stable, or the specific bridge subnet when necessary. Add a NetBird range only if the backend also receives connections from that range.

## Recommended Solution

Trust the smallest set of addresses or subnets that covers your proxy connections. Avoid adding the entire `100.64.0.0/10` or `172.16.0.0/12` range by default.

If the backend sees a proxy's NetBird IP, account for changes when the proxy restarts or recreates its embedded peer. You can use your account's network range if other peers are prevented from connecting directly to the backend. Find the range under **Settings** → **Networks** → [**Network Range**](/manage/settings/networks#network-range), or call `GET /api/accounts` and read `settings.network_range` from the account object in the response array. Accounts can use a custom range outside `100.64.0.0/10`.

<Warning>
    A trusted subnet does not identify the reverse proxy. Any peer or container in that subnet that can connect directly to the backend could supply forged forwarded headers. Restrict access to the backend port with NetBird access policies, host firewall rules, or container network isolation as appropriate for your deployment.
</Warning>

## Service-specific Examples

In the examples below, replace `<PROXY_SOURCE_IP_OR_CIDR>` with the address or subnet identified above. Add separate entries if more than one proxy or forwarding peer can connect to the backend.

### Jellyfin

In the Jellyfin admin dashboard:

1. Go to **Dashboard** → **Networking**.
2. In the **Known Proxies** field, enter the proxy source addresses or CIDR ranges identified above.
3. Click **Save**.

Jellyfin uses this setting to decide whether to accept forwarded client IP, host, and protocol headers. See the [Jellyfin reverse proxy guide](https://jellyfin.org/docs/general/post-install/networking/reverse-proxy/).

For subpath deployments, configure Jellyfin's **Base URL** together with your service's [path and rewrite settings](/manage/reverse-proxy#step-2-configure-service-details).

### Home Assistant

In Home Assistant 2026.8 and later, go to **Settings** → **System** → **Network** and find the **HTTP server** section. Enable **Trust X-Forwarded-For** and add the proxy source addresses or CIDR ranges to **Trusted proxies**. Saving restarts Home Assistant; confirm the settings after the restart within five minutes to avoid an automatic rollback. See the [Home Assistant HTTP documentation](https://www.home-assistant.io/integrations/http/).

On older versions, add or update the `http` section in `configuration.yaml`, then restart Home Assistant:

```yaml
http:
  use_x_forwarded_for: true
  trusted_proxies:
    - "<PROXY_SOURCE_IP_OR_CIDR>"
```

If you use the [NetBird add-on](https://github.com/netbirdio/addon-netbird), check the source reported by Home Assistant before choosing a trusted proxy entry. It may be the add-on's container address; follow the [Docker bridge guidance](#docker-bridge-networks) above.

[![Add NetBird add-on repository](/docs-static/img/manage/reverse-proxy/service-configuration/ha_add_addon_repository.svg)](https://my.home-assistant.io/redirect/supervisor_add_addon_repository/?repository_url=https%3A%2F%2Fgithub.com%2Fnetbirdio%2Faddon-netbird)

Home Assistant rejects proxied requests unless forwarded headers are enabled and the connection source matches a trusted proxy entry. For a full setup walkthrough, see our [Home Assistant guide](https://netbird.io/knowledge-hub/home-assistant-access).

### Nextcloud

In your Nextcloud `config/config.php`, add the proxy source address or subnet to the `trusted_proxies` array:

```php
'trusted_proxies' => ['<PROXY_SOURCE_IP_OR_CIDR>'],
```

Nextcloud accepts IPv4 and IPv6 addresses and CIDR ranges. It reads `X-Forwarded-For` by default for requests from trusted proxies. See the [Nextcloud reverse proxy documentation](https://docs.nextcloud.com/server/latest/admin_manual/configuration_server/reverse_proxy_configuration.html).

## NetBird identity headers

For HTTP services configured with [NetBird-Only Access](/manage/reverse-proxy/authentication#netbird-only-access-private-services), the proxy authenticates the caller through the WireGuard tunnel and forwards the available identity information in these headers:

| Header | Value |
|--------|-------|
| `X-NetBird-User` | The peer owner's email when available; otherwise the peer name. |
| `X-NetBird-Groups` | Comma-separated display names of the calling peer's groups. Falls back to a group ID when its display name is unavailable. |

The proxy omits empty or unsafe header values and skips group labels containing commas or non-ASCII characters. `X-NetBird-Groups` is absent if no valid labels remain. These headers contain display values that can change and need not be unique; do not treat them as immutable user or group identifiers.

<Warning>
    The proxy removes client-supplied `X-NetBird-User` and `X-NetBird-Groups` headers before setting its own values. A client that reaches the backend directly can supply either header itself. Trust these headers only when access to the backend is restricted to the intended NetBird-Only proxy service. Checking that a header is present does not enforce that restriction.
</Warning>

### Example: read the user in a backend

After restricting backend access as described above, this example reads the identity headers and rejects requests without a user value:

```python
from fastapi import FastAPI, Header, HTTPException

app = FastAPI()

@app.get("/me")
def me(
    user: str | None = Header(default=None, alias="X-NetBird-User"),
    groups: str | None = Header(default=None, alias="X-NetBird-Groups"),
):
    if not user:
        raise HTTPException(403, "must be accessed through a NetBird private service")
    return {
        "user": user,
        "groups": groups.split(",") if groups else [],
    }
```

Keep service access rules in NetBird and apply any additional application permissions separately; this example only returns the supplied identity.

## Verifying your configuration

After updating your backend's trusted proxy settings:

1. Access your service through the NetBird reverse proxy URL.
2. Check the backend's resolved client IP against the client address seen by the proxy. A client using NetBird-Only Access can legitimately have a NetBird IP here.
3. If the backend reports the proxy or forwarding peer's address, check that its trusted proxy list matches the connection source, forwarded-header processing is enabled, and the backend has reloaded the configuration.

**Pass Host Header** controls the upstream `Host` header; it does not enable client IP forwarding. If a self-hosted proxy sits behind another proxy or load balancer, also check its [`NB_PROXY_TRUSTED_PROXIES` configuration](/selfhosted/migration/enable-reverse-proxy#networking-and-forwarding).

You can also monitor requests from the NetBird side using [Access Logs](/manage/reverse-proxy/access-logs).
